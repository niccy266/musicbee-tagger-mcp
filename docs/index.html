MusicBee Tagger MCP

A practical guide for investigating audio metadata safely. Human operators use the CLI to review and apply changes; MCP agents use tokens to inspect, verify, and stage proposals.

Safety model

  • No MCP tool accepts playlist or audio paths. Register playlists yourself in a separate local terminal; only opaque tokens are sent through MCP.
  • Never echo, log, or send absolute audio or playlist paths to an agent. The local registration command outputs only tokens, bare filenames, and path-free skip reasons.
  • MCP tools do not write audio. A successful stage creates a pending manifest, not a tag edit.
  • Only the user-controlled CLI applies staged edits. Review the diff before answering yes to its prompt.

Agent boundary: Do not run the apply CLI or otherwise modify audio files. Staging is allowed only after candidate verification passes. Human-only registration keeps paths out of MCP calls, but it is not a Windows security boundary against an agent with unrestricted shell access as the same user.

Human operator: setup, review, apply

From the repository root in PowerShell, create the environment and install this checkout:

py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e .

Configure your MCP client to launch the installed stdio server. For a VS Code workspace, add a server entry to .vscode\mcp.json and replace the placeholders with your local checkout path:

{
  "servers": {
    "musicbee-tagger": {
      "type": "stdio",
      "command": "<checkout>\\.venv\\Scripts\\python.exe",
      "args": ["-m", "musicbee_tagger_mcp.server"],
      "cwd": "<checkout>"
    }
  }
}

To register a playlist without exposing its path to the agent, open a separate PowerShell window (not the agent-controlled terminal) and run the human-only registration command. Enter the playlist path at its prompt, then paste only the returned tokens into the agent conversation:

.\.venv\Scripts\musicbee-tagger-register-playlist.exe

For the release installation, run K:\bin\musicbee-tagger-register-playlist.cmd instead. Path-to-token mappings are stored under K:\tools\mcp-servers\musicbee-tags\data\registered\ and persist across MCP restarts and logins for the same Windows user. After the agent reports staged proposals, inspect them in the terminal:

.\.venv\Scripts\python.exe -m musicbee_tagger_mcp.apply_staged --list
.\.venv\Scripts\python.exe -m musicbee_tagger_mcp.apply_staged --all --dry-run

Apply one proposal interactively, or all pending proposals interactively:

.\.venv\Scripts\python.exe -m musicbee_tagger_mcp.apply_staged --stage-id <UUID>
.\.venv\Scripts\python.exe -m musicbee_tagger_mcp.apply_staged --all

The CLI asks before each write and creates a backup by default. Do not use --no-backup unless you have an intentional reason to skip backups. --dry-run previews without writing.

To run tests after local changes:

$env:PYTHONPATH='src'
.\.venv\Scripts\python.exe -m pytest -q

To preview this guide locally from the repository root, run py -m http.server 8000 --directory docs and open http://localhost:8000 in a browser.

Windows desktop release and Claude Code

The release bundle contains a Python wheel, source distribution, Windows installer, standalone Claude Code MCP config, and a Claude Code plugin marketplace. Extract the release bundle, then install the wheel into a dedicated environment:

.\install.ps1 -WheelPath .\musicbee_tagger_mcp-0.1.2-py3-none-any.whl

The installer defaults to K:\tools\mcp-servers\musicbee-tags\, stores stage data under data\staged\ and private token mappings under data\registered\, and creates K:\bin\musicbee-tagger-mcp.cmd, K:\bin\musicbee-tagger-apply.cmd, K:\bin\musicbee-tagger-register-playlist.cmd, and K:\bin\musicbee-tagger-clear-registrations.cmd. Existing data is preserved during reinstall. Close MCP clients before upgrading; the installer refuses to run while the server process is active. Override -InstallRoot or -BinRoot only if the MCP config and plugin launcher paths are updated to match.

To install the MCP server into Claude Code's user scope from PowerShell, load the provided release/claude-code/mcp-config.json entry:

$server = (Get-Content .\mcp-config.json -Raw | ConvertFrom-Json).mcpServers.'musicbee-tagger'
$json = $server | ConvertTo-Json -Compress -Depth 10
claude mcp add-json --scope user musicbee-tagger $json
claude mcp get musicbee-tagger

Alternatively, add the extracted claude-marketplace directory with claude plugin marketplace add .\claude-marketplace, then install it with claude plugin install musicbee-tagger@musicbee-tagger. The plugin includes the model-invocable musicbee-investigator skill. After extracting a newer release over the existing marketplace directory, run claude plugin marketplace update musicbee-tagger and claude plugin update musicbee-tagger@musicbee-tagger, then restart Claude Code. The MCP process and apply CLI share the private data root through MUSICBEE_TAGGER_DATA_DIR; manually invoking the CLI requires setting the same variable first.

Pending stage manifests, token-to-path registrations, and the shared operation queue are persisted in the install's data folder. Back it up to preserve them. Clear registrations after use with K:\bin\musicbee-tagger-clear-registrations.cmd; the command asks for confirmation and does not remove staged proposals or queue items. Search logs, applied-record archives, retry queues, and confidence-based auto-staging are not part of this release.

MCP agent: investigation procedure

  1. Receive human-registered tokens. Never request or pass a playlist/audio path in chat, MCP, or an agent-controlled terminal. Ask the user to run K:\bin\musicbee-tagger-register-playlist.cmd in a separate PowerShell window and paste the returned tokens.
  2. Read one batch brief. Call get_batch_brief(tokens). Use embedded tags, duration, and filename clues. Filename artist/title order is ambiguous.
  3. Repair text carefully. Use repair_mojibake when encoding appears corrupted. Treat filename clues as hypotheses, not facts.
  4. Search and corroborate. Call search_canonical_release with a plausible artist, title, duration, and useful clues. Use web research for weak, conflicting, or incomplete matches. Record reliable source links when they affect a decision.
  5. Verify every candidate. Call verify_mbid with the candidate recording ID and expected title, artist, and duration. Require verified: true, confidence at least 75, duration difference no more than 6 seconds, and no important mismatch. A passing recording check does not establish the correct album/release.
  6. Preview, then stage. Call preview_tags; propose only supported fields corroborated by evidence. Stage only a non-empty, reviewed diff using stage_tag_changes.
  7. Report and stop. Confirm staged names, fields, confidence, and duration difference using list_staged_changes. Explain unresolved tracks and why. Tell the user to review/apply in the CLI; do not apply changes yourself.

Token mappings persist in the configured data directory and survive MCP restarts and logins for the same user and install. Return concise per-track results instead of full raw responses. Respect the MusicBrainz limit of one request per second; never parallelize requests to evade it.

For work that spans sessions or agents, use enqueue_operation to add a path-free task, list_operations to inspect the shared persistent queue, claim_operations to atomically take a batch, and complete_operation to record each outcome. All agents connected to the same server data directory see the same queue. Queue text and results must not contain filesystem paths.

Never request, repeat, or delegate playlist/audio paths. Tokens may be shared with a subagent only if it can access the same MCP server and local registration store; otherwise perform token-dependent verification and staging in the parent.

The detailed agent workflow is also available in the investigator skill.

Project layout

  • src/musicbee_tagger_mcp/server.py — small MCP app assembly and stdio entrypoint; tool implementations live in tools/, grouped by domain.
  • src/musicbee_tagger_mcp/musicbrainz_client.py — compatibility facade; API setup, shared scoring, search, and verification live in focused sibling modules.
  • src/musicbee_tagger_mcp/file_registry.py, register_playlist_cli.py, and playlist.py — persistent token registration, human-only playlist handoff, and M3U/M3U8 parsing.
  • src/musicbee_tagger_mcp/metadata_reader.py and filename_parser.py — embedded metadata and filename clues.
  • staging.py and stage_manifest_store.py — pending proposals and manifest persistence; staged_apply.py, tag_applier.py, and tag_format_writers.py — CLI-only physical audio writes. MCP preview uses tag_preview.py.
  • queue_store.py and tools/queue.py — transactional, persistent, path-free batch-operation queue shared by MCP clients using the same data directory.
  • tests/ — regression tests; .agents/skills/musicbee-investigator/SKILL.md — detailed agent procedure; docs/index.html — this human/agent web guide.

The package keeps focused service modules for shared logic and groups MCP tool implementations by domain. Treat ~100 lines as a review signal, not a hard limit; preserve cohesive responsibilities instead of splitting solely to meet a number.

Matching and release guidance

  • A MusicBrainz recording is the performance/version candidate; a release is a particular edition; a release group groups related editions. Do not infer a release from recording verification alone.
  • Duration is useful evidence, not proof. Compare title and artist credit, release context, embedded tags, and reliable web sources; treat ambiguous artist/title order and filenames as clues.
  • Keep canonical script and spelling, including Cyrillic and Japanese text, when supported by reliable evidence. Do not strip meaningful live, demo, regional, or version details.
  • When evidence conflicts or a candidate fails verification, leave it unstaged and explain the uncertainty.

Feature proposals

Batch MusicBrainz search

The current MCP surface has one MusicBrainz search tool per candidate query; there is no batch-search tool yet. MusicBrainz's Search API accepts one Lucene query per request. Combining unrelated titles into one Lucene expression does not provide independent per-track ranking, so it is not a safe substitute for separate searches.

A future search_canonical_releases_batch MCP wrapper is a small-to-moderate change: it can accept a list of per-track query objects, deduplicate identical inputs, search sequentially at the service's rate limit, and return compact per-track results. A bounded in-memory cache can avoid duplicate work within the process. This reduces agent/MCP call overhead, but it cannot reduce the number of distinct MusicBrainz HTTP requests or their rate-limit time floor.

Proposed safeguards for that wrapper: validate and cap batch size, deduplicate normalized queries, keep sequential rate limiting, isolate per-track errors, avoid caching transient failures, and test cache keys/expiration and privacy-safe output. A minimal version is a few hours of focused work; production-ready retry and cache tests could make it roughly a half-day to a day, depending on how much resilience is desired.

Persistent state and database evaluation

Consider replacing staged-change JSON manifests with a database only if measured needs justify it, such as durable searchable stage history, concurrent clients, or multi-user operation. Token mappings and stage manifests are persisted as local JSON records; metadata is read from audio files on demand. A database is not expected to speed up audio metadata reads or physical tag writes.

Before choosing a backend, benchmark registration, metadata reading, MusicBrainz requests, stage creation/listing, and CLI apply separately. For a single-user local stdio server, evaluate SQLite first because it provides transactional durable state without requiring a separate server. Consider PostgreSQL if the product becomes a shared service or needs multi-user concurrency, and account for authentication, per-user ownership, schema migrations, backups, and operations.

Any persistent backend must preserve the path privacy and user-controlled write model: restrict access to stored paths, never expose them in MCP responses or logs, isolate records by session/user, and keep physical audio writes exclusive to the explicit user-controlled CLI. A remote database does not give a remote MCP host safe access to audio files on a user's computer. Treat this as an evaluation proposal, not a decision to adopt PostgreSQL.

Module organization

Several Python modules currently exceed the preferred 100-line guideline. Treat that number as a refactoring signal, not a hard limit: split cohesive responsibilities when editing those modules, keep tests aligned, and avoid splitting merely to hit a line count.
